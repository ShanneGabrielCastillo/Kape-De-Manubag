# Customer Digital Receipts for Kape De Manubag

This change adds two customer-facing receipt endpoints — an HTML view and a PDF download — gated behind `order.is_paid` and accessed via the existing `tracking_token` mechanism. `xhtml2pdf==0.2.16` is added as the sole new dependency. The tracker page and its JS are updated to show receipt buttons after payment is confirmed, updating in real time through the existing polling/SSE path.

Watch for: **(confirmed)** The `customer_receipt_unavailable.html` template links to `orders:payment_waiting`, but that view shows Cash/GCash payment instructions — a customer whose order is already `preparing` or `ready` will see a "Go to the cashier" prompt on an already-paid order. **(confirmed)** `test_invalid_token_cannot_access_another_order_receipt` does not test cross-order isolation; it GETs `order2`'s URL with `order2`'s own token and asserts `order2`'s data appears — the invariant stated in the docstring is not exercised.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The payment gate is enforced server-side in both the HTML and PDF views with `if not order.is_paid: return render(..., status=403)`. Both views use `get_object_or_404` against `tracking_token`, so invalid tokens return 404. The views are pure reads — no `save()`, `update()`, or signal call touches any order, payment, or inventory record, verified by three tests.

`gcash_proof` is excluded from the `only()` queryset in both views and appears nowhere in either receipt template. A dedicated test confirms no Cloudinary path leaks into the customer response.

Both views reuse the same `get_object_or_404(..., tracking_token=tracking_token)` pattern as every other customer-facing view — no re-implementation. Receipt templates read `item.unit_price` and `item.subtotal` from `OrderItem` snapshot fields.

The `customer_receipt_unavailable.html` template links to `orders:payment_waiting`. That URL works for any status — it does not crash — but displays Cash/GCash payment instructions designed for `awaiting_payment`. A customer who saved the receipt URL before payment and opens it again after the order moves to `preparing` sees a page telling them to go to the cashier. The `orders:order_tracker` link on the same page is the safer target for this state.

`xhtml2pdf==0.2.16` is pinned exactly. No other dependency is modified.

Test coverage is broad: 18 tests cover all four unpaid-gate scenarios, both payment paths, snapshot-price correctness, packaging fee display, PDF magic-byte validation, 404 on bad tokens, read-only invariants, and staff receipt regression. One test (`test_invalid_token_cannot_access_another_order_receipt`) has a logic error: it asserts the correct behavior for a valid token but never constructs the cross-order case described in its docstring.

1. **Misleading unavailable-page redirect** — `customer_receipt_unavailable.html` links to `orders:payment_waiting` as "View Payment Status". For an order in `preparing` or `ready` (paid, but customer bookmarked the receipt link early), this sends them to a page with payment prompts for an already-completed transaction. Change the primary CTA to `orders:order_tracker` so customers land on the relevant status view. Severity: LOW.

2. **Broken cross-order token isolation test** — `test_invalid_token_cannot_access_another_order_receipt` constructs `wrong_token_url = reverse('orders:customer_receipt', args=[order2.tracking_token])`, GETs it, and asserts `order2.order_number` is present and `order1.order_number` is absent. This is a valid-access test for `order2`, not a cross-isolation test. The isolation property (that `order2`'s token cannot reach `order1`'s receipt data) requires a URL constructed from `order1`'s `tracking_token` and a request that holds only `order2`'s token context — which this test never attempts. A 404 from a valid order's URL is not achievable through normal HTTP (the URL is tied to the token), so the correct test would confirm that you cannot derive `order1`'s URL from `order2`'s token, or at minimum construct a mangled-token URL for `order1` and assert 404. Severity: MEDIUM — a stated security property remains unverified by the test suite.

## Payment gate and unavailable-page redirect

`customer_receipt` and `customer_receipt_pdf` each call `get_object_or_404(..., tracking_token=tracking_token)` then immediately check `if not order.is_paid`. An unpaid order renders `customer_receipt_unavailable.html` with HTTP 403. This covers all four pre-paid states: unpaid Cash, GCash/none, GCash/pending, GCash/rejected.

The unavailable template contains:

```html
<a href="{% url 'orders:payment_waiting' order.tracking_token %}" class="btn btn-primary">
  💳 View Payment Status
</a>
```

`payment_waiting` does not crash for non-`awaiting_payment` statuses, but it renders the GCash screenshot form and "Go to the cashier" instruction block — content that has no relevance once the order is paid and preparing. A customer who opens a stale bookmarked receipt URL (before the receipt was ready), or returns after the kitchen has started their order, is shown payment instructions. The existing "← Back to Order Tracking" link on the same page resolves this, but it is styled as a secondary action. The primary CTA should point to the tracker.

## Cross-order token isolation test gap

The test docstring says: "Order2's token must not grant access to Order1's receipt." The implementation:

```python
order1 = self._make_order(payment_method='cash', is_paid=True)
order2 = self._make_order(payment_method='cash', is_paid=True)
wrong_token_url = reverse(
    'orders:customer_receipt', args=[order2.tracking_token]  # ← order2's own URL
)
response = self.client.get(wrong_token_url)
self.assertEqual(response.status_code, 200)
content = response.content.decode()
self.assertIn(order2.order_number, content)
self.assertNotIn(order1.order_number, content)  # trivially true
```

`order2.tracking_token` maps to `order2`'s row. This is a successful receipt access for `order2`. `order1.order_number` not appearing is trivially true — `order1` was never mentioned in the URL. The token isolation property is enforced by `get_object_or_404(..., tracking_token=tracking_token)`, which makes it impossible to reach `order1` via `order2`'s token. That property is sound in the implementation but the test does not verify it.

A corrected test would use a URL with `order1`'s `tracking_token` directly (this is the only way to reach `order1`'s receipt) and verify a 404 is returned when `order1`'s token is not known to the requester — or, more practically, construct a random token and assert 404, which `test_invalid_tracking_token_receipt_returns_404` already does. The two-order test is misleadingly named and should either be removed or rewritten to test something the existing tests do not already cover.
