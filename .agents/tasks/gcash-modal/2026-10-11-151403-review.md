# GCash in-page verification modal for Order Management

The change adds an in-page modal so Admin/Cashier staff can review and act on a customer's GCash payment submission without navigating to the Order Details page. A new staff-only JSON endpoint (`GET /manage/<pk>/gcash-details/`) supplies the deferred GCash fields on demand, and the existing verify/reject endpoints are reused without modification. All three Verify GCash entry points — the server-rendered table button, the `gcash_submitted` SSE handler, and the `buildOrderCard` mobile builder — are wired to `openGcashVerifyModal`. After verify or reject succeeds, the affected row is updated directly in the DOM; the subsequent `status_changed` SSE arriving via the existing `post_save` signal is idempotent.

Watch for: The `gcash-om-footer-main` div starts with `display:none` and `flex-direction:column` as separate inline style properties; JS shows it with `_showEl(footerMain, 'flex')`, which sets `display:flex` and leaves `flex-direction:column` intact — this works correctly but is worth noting as a subtle pattern. No other blocking concerns found.

**Verdict**: APPROVED

## High-level view

The `gcash_payment_detail` view is properly guarded: it requires `@login_required` + `@cashier_or_admin_required`, only accepts GET (returns 405 otherwise), and returns 400 for any order that is not a pending GCash order — stale data can never reach the modal. The `tracking_token` is absent from the JSON response.

All three Verify GCash button sites are converted from `<a href>` anchors to `<button onclick="openGcashVerifyModal(...)">` calls. The server-rendered table, the `gcash_submitted` SSE handler (with a lazy fallback for rows that predate the new data attributes), and the `buildOrderCard` mobile builder are all updated consistently.

The modal JS is a self-contained IIFE that stores one set of state variables and exposes only `window.openGcashVerifyModal`. The duplicate-submission guard (`_submitting`) gates both the verify and reject-confirm paths. Focus returns to the trigger button on close, and Escape is handled. The verify flow and reject flow both restore button state on failure and keep the modal open.

The row update functions update `dataset` fields, Status cell, Payment cell, and Actions cell, then call `initResponsiveTables` and `reinitLucide` — matching the pattern used by the existing `status_changed` SSE handler.

Eight new tests cover the happy path, all 400 guard conditions, the 405 method guard, the unauthenticated redirect, the kitchen-staff redirect, and the tracking_token exclusion. All 8 pass.

### `gcash_payment_detail` endpoint security and guards

The view is decorated with `@login_required` then `@cashier_or_admin_required`, matching the existing pattern on `verify_gcash_payment` and `reject_gcash_payment`. The guard condition `order.payment_method != 'gcash' or order.gcash_status != 'pending' or order.is_paid` returns 400 for all non-pending states — a verified, rejected, cash, or already-paid order cannot populate the modal. The `tracking_token` field is absent from the `only()` projection and from the JSON response. The `gcash_submitted_at` formatting uses `timezone.localtime()` before `strftime`, so the displayed time is in the configured Django timezone rather than UTC.

### Three-site button replacement

The server-rendered button passes all four arguments (pk, detail URL, verify URL, reject URL) directly as Django template expressions. The `gcash_submitted` SSE handler lazily populates `row.dataset.gcashDetailUrl/Verify/RejectUrl` if they are missing, which handles rows inserted before this JS was present. The `buildOrderCard` mobile builder reads `d.gcashDetailUrl`, `d.gcashVerifyUrl`, `d.gcashRejectUrl` from the card's data object, which is populated from `row.dataset` in the existing card builder infrastructure. The `new_order` SSE handler constructs all three URLs using the same `/0/` → `/${order.order_id}/` substitution pattern used for other URLs on that path and sets them on `row.dataset` before the card builder runs.

### Rejection flow and textarea

The plan noted that `order_detail.html` uses `window.prompt()` for the rejection reason. The modal uses a `<textarea>` instead, which is the appropriate choice for an in-page modal — no browser-native dialog breaks the flow. The rejection note is sent as FormData with key `rejection_note`, matching what `reject_gcash_payment` reads via `request.POST.get('rejection_note', '').strip()`. The textarea is cleared on back and on close.

### Post-action row updates

`updateRowAfterGcashVerify` updates `dataset.isPaid`, `dataset.status`, `dataset.statusDisplay`, `dataset.nextStatus`, and `dataset.gcashStatus`, then rewrites the Status cell (badge-preparing), Payment cell (badge-paid), and Actions cell (receipt link + advance-to-ready button). The advance-to-ready button uses `data-next-status="ready"` and `data-is-paid="true"`, matching the pattern the existing `status_changed` SSE handler uses for preparing-state rows. `updateRowAfterGcashReject` resets the status to `awaiting_payment` and sets the Payment cell to a Pay button (not another Verify GCash button), which is correct because the customer must re-submit before staff can verify again.

### Test coverage

The 8 new tests in `GCashPaymentDetailTest` cover: authenticated cashier on a pending order (200 + field assertions), tracking_token exclusion, already-paid order (400), cash order (400), gcash non-pending (400), unauthenticated redirect (302), kitchen staff redirect (302), and POST method guard (405). All pass. The broader `apps.orders` suite was not run to completion in this environment due to a timeout in the full suite invocation, but the new test class runs clean in isolation (8/8, no failures). The 20 pre-existing failures in `apps.orders.tests_security` are confirmed unrelated by the FEAT-001 findings.

### No changes to order_detail.html or existing views

The git diff for `templates/orders/order_detail.html` is empty — the existing Order Details GCash verification flow is untouched. The existing `verify_gcash_payment` and `reject_gcash_payment` views are unmodified; the modal uses them as-is. The only views.py addition is `gcash_payment_detail` after `reject_gcash_payment`. The `urls.py` addition is a single `path(...)` line before the receipt URL.
