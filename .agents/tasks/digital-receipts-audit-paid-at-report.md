### Payment-Confirmation Paths Updated

1. **`process_payment`** (`apps/orders/views.py`, `POST /orders/manage/<pk>/payment/`)  
   — Handles Cash (Order Management + POS) and onsite GCash.  
   — `paid_at` set here.

2. **`verify_gcash_payment`** (`apps/orders/views.py`, `POST /orders/manage/<pk>/gcash/verify/`)  
   — Handles remote GCash (customer submitted reference, staff verifies).  
   — `paid_at` set to the same `now` as `gcash_verified_at`.

No other legitimate paths set `is_paid = True`.

### Duplicate Confirmation Preserves Original `paid_at`

Both payment paths use the same guard pattern:

```python
if not order.paid_at:
    order.paid_at = timezone.now()
order.is_paid = True
order.save()
```

In `process_payment`, the outer idempotency guard (`if order.is_paid: return error`) fires before `paid_at` is ever set on a second call, making the inner guard a belt-and-suspenders safety net. In `verify_gcash_payment`, the same outer guard (`if order.is_paid: return error`) prevents any second write.

### Receipt Timestamp Behavior

**New orders (paid_at is set):**

```
Confirmed At    |  Apr 25, 2025 2:34 PM
```

Both HTML and PDF display `order.paid_at|date:"M d, Y g:i A"`.

**Historical GCash orders (paid_at=None, gcash_verified_at set):**

```
Confirmed At    |  Apr 20, 2025 10:12 AM  (GCash verification time)
```

Uses `gcash_verified_at` with a note. This is safe because the audit confirmed `gcash_verified_at` is set by staff at the moment of GCash verification — it genuinely represents confirmed payment, not screenshot submission.

**Historical Cash / legacy orders (both timestamps None):**

```
Confirmed At    |  Confirmation time unavailable
```

No fabricated timestamp. The receipt is still valid and all other fields are accurate.

HTML and PDF use identical fallback logic and identical date format (`M d, Y g:i A`).
