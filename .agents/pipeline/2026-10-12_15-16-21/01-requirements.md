# Requirements: Repair Security Tests After Payment-First Ordering Flow

## Summary

`apps/orders/tests_security.py` contains 23 tests that cover rate limiting, tracking-token isolation, and idempotency for anonymous customer orders. As of the baseline run, **20 tests fail and 1 errors out** (21 total affected), while 2 pass. All failures trace back to the test helpers using stale assumptions about the checkout flow. No application regression has been identified; the production code is correct.

The goal is to bring all 23 security tests to passing — and keep all other passing tests passing — by updating the helper methods and one batch of inline test assertions so they match the actual payment-first checkout contract. Security invariants must not be weakened.

---

## Investigation Findings (Baseline: 20 FAIL + 1 ERROR, 2 PASS)

### Root Cause A — `_place_order()` in `TrackingTokenTests` omits `payment_method` (12 tests affected)

`TrackingTokenTests._place_order()` submits only `customer_name` and `order_type`. The live `CheckoutForm` requires `payment_method` as a mandatory `ChoiceField` (choices: `cash`, `gcash`). Without it the form is invalid, the view re-renders the checkout page with HTTP 200, and the method's `assertEqual(resp.status_code, 302)` fails immediately.

Affected tests (all fail at the `_place_order()` assertion):
- `test_new_order_has_tracking_token`
- `test_tracking_token_is_url_safe_length`
- `test_tracking_tokens_are_unique`
- `test_tracking_token_differs_from_order_number`
- `test_tracking_token_differs_from_request_token`
- `test_tracker_page_accessible_with_tracking_token`
- `test_tracker_page_with_order_number_returns_404`
- `test_api_track_accessible_with_tracking_token`
- `test_api_track_does_not_expose_payment_info`
- `test_order_success_page_contains_tracking_link`
- `test_order_success_page_does_not_contain_bare_order_number_tracker_link`
- (and the `test_tracking_tokens_are_unique` loop which also hits the same path)

### Root Cause B — `_place_order_success()` in `OrderRateLimitTests` omits `payment_method` AND asserts the wrong redirect URL (9 FAIL + 1 ERROR)

`OrderRateLimitTests._place_order()` calls `_post_checkout()`, which also submits no `payment_method`. Same form-validation failure → HTTP 200 → `_place_order_success()` asserts `status_code == 302` → `AssertionError: 200 != 302`.

Additionally, `_place_order_success()` asserts `assertIn('/orders/success/', resp['Location'])`. The current checkout view on success redirects to `/orders/waiting/<tracking_token>/` (`orders:payment_waiting`), not to `/orders/success/`. This second assertion would fail even if the status code check were fixed.

The same stale URL literal also appears **inline** in `test_idempotency_replay_does_not_consume_quota`, which tries to read `resp1['Location']` after asserting `/orders/success/` — the missing `Location` header causes a `KeyError`, producing the one `ERROR` result.

And in `test_two_sessions_are_tracked_independently`, `client_b` likewise checks `assertIn('/orders/success/', resp_b['Location'])`.

Affected tests (all fail in `_place_order_success()` or at inline URL assertions):
- `test_first_three_orders_succeed`
- `test_fourth_order_within_window_is_blocked`
- `test_blocked_order_does_not_create_order`
- `test_blocked_order_does_not_deduct_inventory`
- `test_blocked_order_does_not_clear_cart`
- `test_order_allowed_after_window_expires`
- `test_failed_checkout_does_not_consume_quota`
- `test_rate_limit_shows_friendly_message`
- `test_two_sessions_are_tracked_independently` (inline `/orders/success/` assertion)
- `test_idempotency_replay_does_not_consume_quota` (inline assertions + ERROR)

### Root Cause C — No genuine application regression found

The `checkout_view` correctly redirects to `orders:payment_waiting` on success and requires `payment_method`. `Order.tracking_token` is generated by `secrets.token_urlsafe(32)` on every new order save. URLs in `urls.py` include `waiting/<str:tracking_token>/`. The application is correct; only the tests are stale.

### Passing tests (2)

- `test_api_track_returns_404_for_invalid_token` — does not call `_place_order()`
- `test_tracker_page_returns_404_for_invalid_token` — does not call `_place_order()`

## Functional Requirements

### FR-1: Fix `_post_checkout()` module-level helper

`_post_checkout()` must include `payment_method` in its POST payload. The default value shall be `'cash'` (valid choice per `Order.PAYMENT_METHOD_CHOICES`). The function shall accept an optional `payment_method` keyword argument so individual tests can override it when testing a specific payment scenario (e.g. GCash). The existing `customer_name`, `order_type`, and `request_token` parameters are unchanged.

### FR-2: Fix `OrderRateLimitTests._place_order()` helper

`OrderRateLimitTests._place_order()` must delegate to the corrected `_post_checkout()`, ensuring `payment_method='cash'` is included in every checkout POST. No other behavior changes.

### FR-3: Fix `OrderRateLimitTests._place_order_success()` helper

`_place_order_success()` must:

1. Call the corrected `_place_order()` to submit a valid checkout POST.
2. Assert `resp.status_code == 302` (redirect on success — this assertion is correct and must be kept).
3. Assert the redirect location is to `/orders/waiting/` (the `payment_waiting` URL) rather than the obsolete `/orders/success/`. The exact URL contains a tracking token, so the assertion must check that the location starts with `/orders/waiting/` or matches the pattern `orders:payment_waiting`, not that it equals a hard-coded path.
4. Return `resp` so callers can inspect it if needed.

### FR-4: Fix `TrackingTokenTests._place_order()` helper

`TrackingTokenTests._place_order()` must include `payment_method='cash'` in the `_post_checkout()` call. The helper returns the latest `Order` object; this behavior is unchanged.

### FR-5: Fix inline `/orders/success/` assertions in `test_idempotency_replay_does_not_consume_quota`

The inline `assertIn('/orders/success/', resp1['Location'])` and `assertIn('/orders/success/', resp2['Location'])` must be updated to assert against the current payment-waiting URL pattern (i.e., `/orders/waiting/`). The core security assertions — that exactly one order is created, the idempotency key is not double-counted in the rate-limit session, and the timestamp list has exactly 1 entry — must be preserved unchanged.

### FR-6: Fix inline `/orders/success/` assertion in `test_two_sessions_are_tracked_independently`

The `assertIn('/orders/success/', resp_b['Location'])` for `client_b` must be updated to the current payment-waiting URL pattern. The security assertion — that session B can still place an order after session A exhausts its quota — is unchanged.

### FR-7: Preserve all security coverage

No test may be deleted, skipped, or have its security invariant weakened. The following coverage areas must remain intact:

- Anonymous order rate limiting (max orders per window, blocked orders, quota consumption rules)
- Order idempotency / duplicate-request protection
- Tracking-token generation, uniqueness, and URL-safe length
- Tracker page and API access via token only (order number alone returns 404)
- API response does not expose payment fields
- Success page links to secure tracker URL
- Success page does not expose bare order number as tracker URL
- Session isolation (independent quota per session)
- Friendly rate-limit error message content

### FR-8: No production code changes

The checkout view, payment service, receipt view, inventory logic, and all models must not be modified unless a genuine defect is demonstrated. Based on the investigation, no defect exists; no production changes are required.

### FR-9: CustomerReceiptTests and PaidAtTimestampTests unaffected

The 19 `CustomerReceiptTests` and 12 `PaidAtTimestampTests` in `tests.py` must continue to pass. Changes are confined to `tests_security.py`.

## Non-Functional Requirements

- **Minimal diff**: Changes must be limited to `apps/orders/tests_security.py`. If `_post_checkout()` is a module-level helper defined in the same file, it is updated in place. No new test files, no new fixtures, no new helper modules.
- **No database bypass**: Tests must not set `is_paid=True` or `paid_at` directly to make orders appear paid unless the specific test is explicitly testing post-payment behavior (none of the 20 failing tests require a paid order).
- **No hard-coded tokens**: Tracking tokens must be extracted from the actual redirect URL, not hard-coded.
- **Readability**: Updated helpers must include a brief comment noting the `payment_method` addition and the new redirect target so future maintainers understand why the helpers look the way they do.

## Assumptions

1. `payment_method='cash'` is the correct default because: (a) the `CheckoutForm` uses `initial='cash'`, (b) the existing passing tests in `tests.py` all use `'cash'`, and (c) the failing security tests cover rate limiting and tracking-token logic that is payment-method-agnostic — cash is the simplest valid value.
2. The correct URL pattern name for the post-checkout redirect is `orders:payment_waiting` with path `/orders/waiting/<tracking_token>/`. This was confirmed from `urls.py` and the `checkout_view` success path in `views.py`.
3. The `_place_order_success()` assertion on the redirect URL should check for the prefix `/orders/waiting/` (not an exact match) because the tracking token varies per test run.
4. `test_idempotency_replay_does_not_consume_quota` requires extracting the tracking token from `resp1['Location']` rather than asserting a static string; the duplicate-order path in the view redirects idempotency replays to `payment_waiting` as well (confirmed in `views.py`).
5. No test in the failing set requires the order to be marked `is_paid=True`; all are testing pre-payment checkout and token behavior.
